# Решения и их обоснование

Каждое решение описано по схеме из требований: **что сделано → почему → альтернативы →
эксперимент → результат → почему выбрано**. Таблицы с цифрами — в
[experiments/REPORT.md](experiments/REPORT.md), сырые результаты — в `experiments/results/*.json`.

Как читать цифры. Тестовый набор — 47 вопросов: 39 с ответом и 8 без ответа в документации.
Один вопрос из 39 меняет Hit@1 или Evidence@K на 0,026, поэтому для главных метрик посчитан
95% bootstrap-интервал. Если интервалы двух вариантов сильно перекрываются, это **не**
доказательство, что один лучше; тогда выбираю более простой или дешёвый вариант и пишу об
этом прямо.

Где идея взята из работы одногруппника (Kubernetes Docs Grabber, .NET), это отмечено
пометкой **[референс]** с объяснением, почему она подходит сюда. Код не копировался: другой
язык, другой корпус, другая архитектура.

## 1. Корпус: документация Odoo 18 Inventory + Barcode

**Что сделано.** Источник: репозиторий `odoo/documentation`, ветка `18.0`, папки
`inventory_and_mrp/inventory` и `inventory_and_mrp/barcode`. 102 RST-файла; после очистки 94
документа (8 страниц короче 200 символов отброшены), 703 секции, ~560 тыс. символов.

**Почему.** Документация реальная, живая (коммиты каждый день, так что инкрементальный сбор
проверяется на настоящих изменениях), с понятной структурой и множеством конкретных фактов
(пути в меню, названия настроек, коды вроде SGTIN-96). Объём подходит для CPU: полный индекс
строится меньше чем за минуту, поэтому можно прогнать десятки экспериментов.

**Альтернативы.** Вся документация Odoo (тысячи страниц, индексация на CPU часами); только
Barcode (слишком мало, ~15 страниц); документация Kubernetes (её уже взял одногруппник).

**Результат.** Корпус покрывает все 39 вопросов с ответом; проверка `validate_dataset`
подтверждает, что каждая evidence-фраза реально есть в документах.

## 2. Сбор данных (grabber)

**Что сделано.** `git clone --filter=blob:none --depth 1 --sparse` только нужных папок, затем
`git ls-tree` даёт blob SHA каждого файла. SHA сравнивается с локальным `manifest.json`:
новый путь → скачать (`active`); тот же путь, другой SHA → перекачать (`updated_at`); тот же
SHA → пропустить; путь пропал → статус `deleted` и удаление сырой копии. Одинаковое содержимое
под двумя путями помечается `duplicate_of`. Есть lock от параллельного запуска, атомарная
запись manifest и журнал `sync_log.jsonl`. Ошибка в одном файле не останавливает прогон.

**Почему.** blob SHA считает сам GitHub, так что вопрос «изменился ли файл» сводится к сравнению
строк. git не имеет лимита 60 запросов/час, как REST API без токена, и не требует хранить токен.
Sparse checkout не тянет ~550 скриншотов.

**Альтернативы.** GitHub REST API (лимиты, нужен токен); скачивание HTML с сайта odoo.com
(теряется структура RST, надо парсить вёрстку, нет хэшей); полный clone (сотни МБ картинок).

**Эксперимент.** Первый запуск занял ~3,5 мин. Первая версия проверки изменений через
`ls-tree -l` тоже шла 3,5 мин, потому что запрашивала размеры blob-ов с сервера. После
исправления повторный запуск: **2 с**, `unchanged=102`, новых/изменённых/удалённых 0.
Удаление и дубликаты проверены тестами на фейковом источнике (`tests/test_grabber.py`).

**[референс]** Идея «blob SHA против локального manifest + статус удаления вместо физического
стирания» взята у одногруппника (у него PendingDeletion в MongoDB). Подходит и здесь: источник
тоже git-репозиторий, а статус `deleted` позволяет потом убрать chunks из индекса, не теряя
историю. Хранилище другое: у нас файлы + JSON, потому что 102 файла не требуют СУБД.

## 3. Предобработка: собственный RST-парсер

**Что сделано.** Парсер превращает RST в дерево: заголовок документа → секции с путём
заголовков → блоки (`paragraph`, `list`, `note`, `table`, `code`, `caption`). Роли Sphinx
(`:guilabel:`, `:menuselection:`) раскрываются в текст («Inventory > Configuration >
Settings»), ссылки `:ref:`/`:doc:` заменяются реальными заголовками целевых страниц, таблицы
переводятся в строки «поле: значение», картинки выбрасываются (alt-текст по настройке).
Нормализация Unicode NFC и пробелов. Повторная обработка запускается, только если изменились
blob SHA, версия процессора или его параметры.

**Почему.** docutils падает на ролях и директивах Odoo, а полный Sphinx требует собрать весь
репозиторий и выдаёт HTML, из которого снова надо вытаскивать структуру. Структура нужна дальше:
стратегия `section`, контекстный заголовок и ссылки на конкретный раздел (URL с якорем)
строятся именно из неё.

**Альтернативы.** docutils/Sphinx; pandoc (теряет роли Sphinx); удаление разметки регулярными
выражениями (теряются секции, таблицы превращаются в мусор).

**Результат.** 94 документа, 703 секции, 2653 блока. 7 тестов на парсер
(`tests/test_rst_parser.py`).

## 4. Chunking

**Что сделано.** Четыре стратегии с одинаковыми metadata (документ, путь секций, URL с якорем,
модуль): `fixed`, `fixed_overlap`, `paragraph`, `section`. По умолчанию **`section`, 1000
символов, overlap 0**: одна секция = один chunk, длинная секция режется по блокам, крошечная
склеивается с соседней.

**Почему такая метрика.** Сравнивать стратегии по MRR нечестно: при крупных chunks в Top-5
попадает больше текста. Поэтому каждому варианту дан **одинаковый бюджет контекста 4000
символов**, и главная метрика `Evidence@ctx`: есть ли evidence-фраза в том тексте, который
реально получит LLM.

**Эксперимент** (`chunking`, hybrid MiniLM+BM25, без reranker, EN):

| Вариант | MRR [95% CI] | Evidence@ctx | chunks |
|---|---|---|---|
| fixed-500 | 0.967 [0.91–1.00] | 0.744 | 1144 |
| fixed-1000 | 0.951 [0.89–1.00] | 0.821 | 593 |
| fixed-2000 | 0.970 [0.93–1.00] | 0.692 | 316 |
| fixed_overlap-1000-o200 | 0.947 [0.88–1.00] | 0.897 | 720 |
| paragraph-1000 | 0.938 [0.88–0.99] | 0.897 | 678 |
| paragraph-1500 | 0.960 [0.90–1.00] | 0.897 | 455 |
| **section-1000** | 0.938 [0.87–0.99] | 0.872 | 938 |
| section-1500 | 0.951 [0.89–1.00] | **0.923** | 794 |

Overlap (fixed-1000): 0 → 0.821, 100 → 0.872, 200 → 0.897, 300 → 0.923.

**Что видно.** Нарезка без учёта структуры (`fixed`) хуже всего доносит ответ до LLM: факт
оказывается разрезан, а большие окна (2000) съедают бюджет одним куском. Overlap лечит разрезы,
но увеличивает индекс на 20–35%. Структурные стратегии (`paragraph`, `section`) дают 0.87–0.92.
Разница между лучшими вариантами — 1–2 вопроса из 39, то есть в пределах шума.

**Почему выбрано section-1000, а не section-1500.** Ограничение модели: MiniLM видит только
256 токенов. Замер без обрезки токенизатора: доля chunks длиннее 256 токенов у section-1000
**0.7%**, у section-1500 **16.8%** (у paragraph-1500 72%, у fixed-2000 86%). Т.е. у 1500 каждый
шестой chunk эмбеддится не полностью, и выигрыш по Evidence@ctx статистически не доказан.
Плюс section-1000 даёт чистые ссылки: chunk = одна секция = один якорь в URL.

**На твоё решение.** Если по результатам ПК основной моделью станет bge-m3 (8192 токена),
ограничение исчезает, и section-1500 становится разумным выбором. Переключение:
`chunking.max_chars: 1500` в `configs/default.yaml`.

## 5. Контекстный заголовок в тексте для embeddings

**Что сделано.** В вектор идёт не только текст chunk, а «Название документа > путь секций» +
текст. В ответ LLM и в BM25 идёт тот же текст с заголовком.

**Почему.** Секция «Configuration» без заголовка не говорит, *что* настраивается; с заголовком
«Wave transfers > Configuration» chunk находится по вопросу о волнах.

**Эксперимент** (`header`, MRR EN): dense **0.936 vs 0.891** (Hit@1 0.872 vs 0.795),
BM25 0.861 vs 0.855, hybrid 0.932 vs 0.923.

**Выбор.** Оставить: заметный плюс для dense, ничего не стоит. **[референс]** У одногруппника
вход в embedding тоже «title + heading path + text»; это стандартный приём, проверен здесь
отдельным экспериментом.

## 6. Embeddings

**Что сделано.** Три бэкенда за одним интерфейсом:
* **MiniLM-L6-v2** через ONNX Runtime (384 измерения, английская, 22M параметров) — по умолчанию;
* **TF-IDF + LSA** (256 измерений) — «нейросеть не нужна?»-baseline;
* **любая модель Ollama** (`bge-m3`, `nomic-embed-text`, `qwen3-embedding:0.6b`) — на ПК.

Векторы кэшируются в SQLite по `модель + sha256(текст)`, поэтому смена chunking или reranker
не пересчитывает одинаковые тексты, а прерванная индексация продолжается.

**Почему MiniLM по умолчанию.** Работает на любом CPU без PyTorch (~80 МБ), индекс из 938
chunks строится за ~27 с, запрос эмбеддится за ~3 мс. В облаке без Ollama и без доступа к
Hugging Face это единственная нейросетевая модель, которую удалось скачать.

**Эксперимент** (`retrieval`, MRR [95% CI]):

| Метод | EN | RU | p50 |
|---|---|---|---|
| BM25 | 0.861 [0.77–0.94] | 0.389 | 3 мс |
| dense TF-IDF | 0.872 [0.77–0.95] | 0.425 | 28 мс |
| dense MiniLM | **0.936** [0.89–0.99] | 0.300 | 3 мс |
| hybrid TF-IDF | 0.889 | 0.393 | 29 мс |
| hybrid MiniLM | 0.932 [0.86–0.99] | 0.424 | 4 мс |

**Главная находка: русские вопросы.** По-английски MiniLM лучший, но на тех же вопросах
по-русски MRR падает до 0.30–0.42: MiniLM обучена на английском, а BM25 не может сопоставить
русские слова с английскими. Это не ошибка кода, а ограничение модели. Решения два, оба
подготовлены и запускаются на ПК (`query_language`): мультиязычная **bge-m3** или **перевод
вопроса на английский** через LLM перед поиском (`retrieval.translate_query: true`).

**На твоё решение после ПК.** Если bge-m3 даёт сопоставимый EN и нормальный RU, сделать её
моделью по умолчанию (`embedding.backend: ollama`, `EMBED_MODEL=bge-m3`). Цена: индексация на
CPU заметно дольше (у одногруппника ~0.7 chunk/с), но кэш делает это разовой работой.

## 7. Векторное хранилище

**Что сделано.** FAISS `IndexFlatIP` по умолчанию; FAISS HNSW и Qdrant (локальный режим) за
тем же интерфейсом.

**Эксперимент** (`vectorstore`): качество одинаковое до третьего знака (MRR 0.936 у всех);
p50 поиска: flat 2.7 мс, HNSW 2.8 мс, Qdrant 5.0 мс.

**Выбор.** На ~1000 векторах точный перебор быстрее любых приближённых индексов, поэтому FAISS
flat. Qdrant оставлен специально для лабораторных 2–3: там он станет отдельным сервисом в
Docker/Kubernetes, и код переключается одной настройкой `vectorstore.backend: qdrant`.

## 8. Поиск: hybrid + RRF, Top-K

**Что сделано.** Dense и BM25 ищут по 50 кандидатов, списки сливаются Reciprocal Rank Fusion
(`1 / (k + rank)`, k = 60), дальше Top-20 идёт в фильтры и reranker. BM25 свой, со стеммингом
Snowball (английский для латиницы, русский для кириллицы).

**Почему hybrid, если dense MiniLM по MRR не хуже.** По EN они равны в пределах шума (0.936 vs
0.932), но hybrid лучше на точных терминах (у BM25 Evidence@5 0.897 против 0.821 у dense) и
устойчивее на RU (0.424 против 0.300). RRF не требует калибровать шкалы cosine (0..1) и BM25
(0..30).

**Эксперимент** (`rrf`): k = 10 → MRR 0.938, k = 60 и 100 → 0.932; глубина списков 20/50/100
не влияет. Разница — один вопрос, поэтому оставлено стандартное k = 60 из статьи про RRF.

**Эксперимент** (`topk`, Top-K кандидатов для reranker MaxSim):

| Top-K | MRR | Evidence@5 | p50 |
|---|---|---|---|
| 5 | 0.974 | 0.872 | 179 мс |
| 10 | 1.000 | 0.872 | 263 мс |
| 20 | 1.000 | 0.872 | 502 мс |
| 50 | 1.000 | 0.846 | 1097 мс |

**Выбор: 20.** 10 уже достаточно на английском наборе, но Recall@20 retriever-а на RU 0.61,
то есть на трудных вопросах ответ часто лежит глубже 10-го места. 50 только медленнее и даже
чуть хуже. Если важна скорость, `retrieval.top_k: 10` почти ничего не теряет на EN.

## 9. Фильтры и отказ при нехватке данных

**Что сделано.** Между retriever и LLM: фильтр по модулю (metadata), минимальная длина 60
символов, порог similarity (по умолчанию выключен), удаление точных и почти-дублей (Jaccard
слов ≥ 0.9), не больше 3 chunks из одного документа. Каждый отброшенный кандидат сохраняет
причину (видно в `/search` и `debug`). **Если после фильтров и reranker ничего не осталось,
система отвечает отказом, не вызывая LLM.**

**[референс]** Набор шагов фильтра (минимальная схожесть, минимальная длина, Jaccard-дубли,
лимит chunks на документ) и «пустой контекст → отказ без LLM» взяты из схемы одногруппника.
Подходят, потому что решают те же проблемы: дубли от overlap-нарезки, один длинный документ,
забивающий весь контекст, и галлюцинации LLM на нерелевантном контексте.

**Эксперимент 1** (`threshold`, порог cosine в фильтре, dense MiniLM, EN):

| Порог | MRR | вопросов с ответом потеряно | вопросов без ответа отсечено до LLM |
|---|---|---|---|
| нет | 0.932 | 0% | 0% |
| 0.4 | 0.932 | 0% | 12.5% |
| 0.5 | 0.904 | 5.1% | 50% |
| 0.55 | 0.885 | 7.7% | 62.5% |
| 0.6 | 0.821 | 15.4% | 75% |
| 0.65 | 0.628 | 33.3% | 87.5% |

Лучший баланс по сбалансированной точности — порог ~0.58 (сохраняется 90% вопросов с ответом,
отсекается 75% вопросов без ответа).

**Эксперимент 2** (`rerank_threshold`, порог на оценку MaxSim): 0.66 на EN теряет 10.3% вопросов
с ответом и отсекает 87.5% вопросов без ответа. Но **на русском любой порог ≥ 0.6 отсекает 100%
вопросов**, в том числе все вопросы с ответом: у MiniLM оценки для русских вопросов просто
ниже.

**Выбор: порога по умолчанию нет.** Отказ обеспечивают строгий промпт LLM (фиксированная фраза
отказа, «отвечай только по контексту») и пустой контекст. Порог зависит от модели embeddings и
от языка, поэтому для bge-m3 подготовлена отдельная калибровка (`threshold_bge_m3`, EN и RU).

**На твоё решение.** Варианты: (а) без порога, отказ решает LLM — рекомендую, пока не
посчитано на ПК; (б) порог 0.66 на MaxSim — меньше вызовов LLM на мусорных вопросах, но
русские вопросы с MiniLM перестают работать; (в) порог по результатам `threshold_bge_m3`, если
перейдёшь на bge-m3.

## 10. Reranker

**Что сделано.** Пять вариантов второго этапа над Top-20 → Top-5: без reranker, bi-encoder
(cosine MiniLM), **MaxSim** (late interaction в стиле ColBERT на токенных векторах MiniLM),
cross-encoder `BAAI/bge-reranker-v2-m3` (мультиязычный, на ПК), LLM-reranker (оценка 0–10
через Ollama, на ПК).

**Эксперимент** (`reranker`):

| Вариант | MRR EN [95% CI] | Hit@1 EN | Recall@5 EN | MRR RU | p50 |
|---|---|---|---|---|---|
| нет | 0.932 [0.86–0.99] | 0.897 | 0.934 | 0.424 | 3 мс |
| bi-encoder | 0.936 [0.89–0.99] | 0.872 | 0.938 | 0.308 | 374 мс |
| **MaxSim** | **1.000** [1.00–1.00] | **1.000** | **0.966** | 0.332 | 466 мс |
| cross-encoder | на ПК | | | | |
| LLM | на ПК | | | | |

**Выбор: MaxSim.** На английском нужный документ на первом месте во всех 39 вопросах; стоит
~0.5 с на CPU, что мало по сравнению с генерацией LLM (секунды). Bi-encoder бесполезен: он
повторяет то же сравнение, что dense-поиск. На русском MaxSim не помогает (та же причина, что
в п. 6). **Осторожно с цифрой 1.000**: набор из 39 вопросов на английском для MaxSim «решён»,
различать варианты дальше он уже не может (см. ограничения).

**На ПК.** Сравнить с cross-encoder bge-reranker-v2-m3: он мультиязычный и должен помочь
русским вопросам. Если выиграет, переключение `reranker.backend: cross_encoder`.

## 11. Генерация ответа

**Что сделано.** LLM через Ollama (`LLM_MODEL=qwen3.5:4b`, альтернатива `qwen3.5:9b`),
`temperature=0`, контекст 6000 символов. Два промпта: `basic` («ответь по контексту») и
`strict` (только контекст, фиксированная фраза отказа, ссылки [n] на источники, язык ответа =
язык вопроса, не выдумывать пункты меню). Ответ содержит источники с названием, секцией и URL
с якорем. Ошибки Ollama (не запущена, нет модели, таймаут) превращаются в понятные сообщения и
HTTP 503. Отдельно есть **extractive-baseline без LLM**: выбирает из контекста предложения,
больше всего похожие на вопрос, и цитирует их.

**Почему так.** Qwen 3.5 бесплатна, локальна и понимает русский; 4B помещается в обычную
видеокарту/CPU, 9B для сравнения качества. Строгий промпт нужен, потому что главная ошибка RAG —
ответ «из головы» модели, а не из документации.

**Эксперимент в облаке** (`generation`, без LLM):

| Вариант | Язык | Правильное поведение | Отказ на вопросах без ответа | Ложные отказы | Покрытие ключевых слов | Точность ссылок |
|---|---|---|---|---|---|---|
| extractive | EN | 0.830 | 0% | 0% | 0.647 | 0.808 |
| extractive + порог 0.66 | EN | **0.894** | 87.5% | 10.3% | 0.769 | 0.881 |
| extractive | RU | 0.447 | 50% | 56.4% | 0.436 | 0.569 |

Extractive отвечает правильно на большинство английских вопросов, но не умеет говорить «не
знаю» без порога и не работает с русскими вопросами (русские слова не совпадают с английскими
предложениями). Это нижняя граница, с которой сравнивается LLM.

**На ПК** (`run_pc_experiments.ps1`): 2 модели × 2 промпта с LLM-судьёй (правильность 0–2 и
опора на контекст), плюс эксперимент `context` (Top-3/5/8 × 3000/6000 символов). Только после
этого можно подтвердить выбор `qwen3.5:4b` + `strict`. **Путь с LLM в облаке проверен только
тестами с фейковым клиентом**; первый настоящий запуск будет на твоём ПК.

## 12. Методика оценки

**Что сделано.** 47 вопросов (`data/eval/questions.jsonl`), каждый на английском и русском:
12 фактических, 11 конкретных (пути в меню, настройки), 8 требующих нескольких документов,
8 контекстных (сценарии), 8 без ответа в документации (зарплата, столица Франции, Kubernetes,
Odoo 19 и т. п.). У каждого вопроса: эталонный ответ, релевантные документы, evidence-фразы
(точные цитаты из документации) и ключевые слова ответа с допустимыми вариантами.

**Почему разметка по документам и цитатам, а не по id chunks.** Id chunk меняется при любой
смене chunking, и разметка, привязанная к одной нарезке, делает сравнение стратегий нечестным.
Документ и цитата от нарезки не зависят. Это сознательное отличие от схемы одногруппника (у
него `relevantNodeIds` для конкретной нарезки).

**Метрики.**
* поиск: Hit@K, Recall@K, Precision@K, MRR, nDCG@K по документам; Evidence@K (цитата есть в
  Top-K); **Evidence@ctx** (цитата есть в том контексте, который реально уйдёт в LLM). Считаются
  отдельно после retriever, после фильтров и после reranker;
* отказ: доля вопросов с ответом, потерянных до LLM, и доля вопросов без ответа, отсечённых до
  LLM; лучший порог по сбалансированной точности;
* генерация: правильное поведение (ответил/отказал когда надо), ложные отказы, покрытие
  ключевых слов, доля ответов со ссылками и точность ссылок, оценка LLM-судьёй;
* время каждого этапа (p50/p95);
* для главных метрик 95% bootstrap-интервал (2000 повторов).

**Равные условия.** Каждый эксперимент меняет один компонент, всё остальное из
`configs/default.yaml`. Эксперименты до reranker (chunking, header, retrieval, rrf, threshold,
vectorstore) идут **без reranker**, иначе MaxSim выравнивает все варианты до MRR ≈ 1.0 и
эффект пропадает.

**[референс]** Набор Hit/Recall/MRR/nDCG@5 по этапам retriever → filter → reranker взят у
одногруппника; добавлены Evidence@ctx, доверительные интервалы, метрики отказа и генерации.

## 13. API, логи и готовность к лабораторным 2–3

**Что сделано.** FastAPI: `/health` (процесс жив), `/ready` (индекс загружен и Ollama
доступна, иначе 503), `/ask`, `/search`, `/config`, Swagger, простая веб-страница. Индекс
грузится в фоне, поэтому `/health` отвечает сразу, а `/ready` — когда можно принимать
запросы (это ровно liveness/readiness probe в Kubernetes). Каждый запрос получает
`X-Request-ID`, который есть в каждой строке лога; логи в JSON по `LOG_FORMAT=json`. Ошибки
единообразны: `{"error", "request_id"}` без stack trace. Все настройки из `.env`, секретов в
Git нет (`.env` в `.gitignore`, шаблон `.env.example`).

**Что помешает в лабах 2–3** (честный список, чтобы решить заранее):
1. **Индекс лежит на локальном диске** (`data/indexes/`). Для нескольких реплик нужен общий
   том или переход на Qdrant как сервис (уже поддержан).
2. **Модели работают внутри процесса API** (MiniLM, MaxSim). Каждая реплика грузит их сама;
   логично вынести embeddings/reranker в отдельный сервис.
3. **Кэш векторов в SQLite** — файл на одном диске; для нескольких сервисов нужен Redis или
   общая БД.
4. **Один процесс делает всё** (индексация + ответы). Grabber/индексацию стоит выделить в
   отдельный job (в Kubernetes — CronJob).
5. Lock grabber-а — файловый; при нескольких экземплярах нужен lock в общем хранилище.

## 13a. Разбор вопроса через LLM (перевод + подвопросы)

* **Что сделано.** Перед поиском каждый вопрос (русский и английский) один раз уходит в LLM
  (`retrieval.rewrite_query`, промпт `REWRITE_PROMPT`). Она возвращает JSON с 1–3 английскими
  поисковыми запросами: перевод, разделение составного вопроса («как включить волны и как
  работают локации?»), бытовые слова → термины Odoo. Поиск, фильтры и reranker идут по каждому
  подвопросу отдельно, их Top-5 сливаются через RRF, поэтому каждая часть вопроса попадает в
  контекст. Генератор получает исходный вопрос; правило 6 строгого промпта: ответить на каждую
  часть и назвать ту, которой нет в документации. Ошибка LLM или неверный JSON → поиск по
  переводу (для не-английского вопроса) или по исходному вопросу.
* **Почему.** На ПК (2026-10-22) русский вопрос без перевода давал ложный отказ: MiniLM знает
  только английский, поиск доставал не те куски. Перевод это исправил (+0,4–0,9 с). Составной
  вопрос терял вторую тему: из Top-20 в Top-5 не попадало ни одного куска про локации.
* **Альтернативы.** Только перевод (`translate_query`, остаётся как запасной вариант);
  многоязычные embeddings bge-m3 без LLM (эксперимент `query_language`); отдельный ответ на
  каждый подвопрос и склейка (2–3 генерации, время ×2–3); проверка темы в том же вызове
  (отклонено Дмитрием: риск ложных отказов, отказ остаётся за строгим промптом).
* **Цена.** Каждый вопрос, даже английский, +1 вызов LLM (~0,5–1 с); LLM может разбить то, что
  разбивать не нужно.
* **Эксперимент.** `python run.py experiment query_rewrite` (none / translate / rewrite, EN и RU).
  Во всех остальных экспериментах разбор выключен, чтобы менялся один фактор.
* **Результат.** Включено по умолчанию по решению Дмитрия до эксперимента; цифры будут здесь
  после запуска на ПК.

## 14. Ограничения

* **Тестовый набор составлен тем же, кто строил систему**, по тексту документации. Вопросы
  поэтому близки к формулировкам документов, и английский набор для MaxSim уже «решён»
  (MRR 1.0). Чтобы различать сильные варианты, нужны твои собственные вопросы, сформулированные
  как у реального пользователя.
* 39 вопросов с ответом: один вопрос = 2.6 п. п. Большинство различий между лучшими вариантами
  в пределах доверительных интервалов.
* LLM, bge-m3, cross-encoder, перевод вопроса и LLM-судья в облаке не запускались (нет доступа
  к Ollama и Hugging Face). Для них написаны эксперименты и скрипт, строки в отчёте помечены
  `skipped`.
* Русские вопросы с текущими моделями работают плохо; это главная задача для ПК.
