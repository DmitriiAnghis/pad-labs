# Лаба 3. Решения и их обоснование

Каждое решение записано по схеме: что сделано → почему → какие были альтернативы → чем
проверено → результат → почему выбрано это. Проверки проводились 2026-11-07 в тестовом
кластере Kubernetes в облаке (k3s v1.31, см. раздел 13 «Как проверялось») и в docker compose.

Термины, которые встречаются ниже:
* **Kubernetes (k8s)** — система, которая запускает контейнеры на одном или нескольких
  компьютерах (узлах), следит, чтобы нужное число копий работало, и перезапускает упавшие.
* **Minikube** — Kubernetes из одного узла на своём компьютере, для учёбы и разработки.
* **Pod** — минимальная единица запуска в Kubernetes: один или несколько контейнеров с общим
  IP-адресом. Обычно один Pod = один контейнер = одна копия сервиса.
* **манифест** — YAML-файл, в котором описано, *что* должно быть в кластере (например,
  «3 копии order-service»). Kubernetes сам приводит кластер к этому описанию.
* **kubectl** — программа командной строки для работы с Kubernetes.

## 1. Структура папки `lab3/k8s` и одна команда развёртывания

**Что сделано.** Манифесты разложены по типу объектов, как в примере из требований:
`namespace.yaml`, `deployments/`, `services/`, `configmaps/`, `secrets/`, плюс
`infrastructure/` (PostgreSQL, RabbitMQ), `jobs/` (индексатор RAG), `storage/` (том RAG),
`ingress/`, `extras/` (автомасштабирование). Всё применяется одной командой
`kubectl apply -k lab3/k8s` через `kustomization.yaml`.

**Почему.** kustomize (встроен в kubectl, отдельно ставить не нужно) делает три вещи, которых
нет у простого `kubectl apply -f`: проходит по подпапкам, ставит всем объектам namespace `pad`
и создаёт Secret из файла, которого нет в Git (раздел 4).

**Альтернативы.**
* `kubectl apply -f lab3/k8s/` — не заходит в подпапки (нужен `-R`) и не умеет создавать Secret
  из файла: Secret пришлось бы создавать отдельной командой.
* Helm (менеджер пакетов Kubernetes с шаблонами) — шаблоны `{{ .Values... }}` делают манифесты
  труднее для чтения; для одной среды (Minikube) параметризация не нужна. Требования Helm не
  упоминают.

**Проверка.** `kubectl apply -k` в тестовом кластере создаёт 28 объектов за один запуск;
`kubectl kustomize lab3/k8s` печатает итоговый YAML без применения.

**Почему выбрано.** Читаемые обычные манифесты + одна команда.

## 2. Deployment для сервисов, StatefulSet для базы и брокера, Job для индексации

**Что сделано.**
* 7 Deployment-ов: auth, catalog, inventory, order, fulfillment, notification, gateway, плюс
  rag-assistant (итого 8).
* PostgreSQL и RabbitMQ — StatefulSet с постоянным томом.
* rag-indexer — Job (разовая задача).

**Почему.**
* **Deployment** — для сервисов без своего состояния: все данные у них в базе, поэтому копии
  взаимозаменяемы, их можно удалять и добавлять в любой момент.
* **StatefulSet** — для программ, которые сами хранят данные на диске. У Pod-а постоянное имя
  (`postgres-0`) и свой PVC (PersistentVolumeClaim, запрос на постоянный диск), который не
  удаляется вместе с Pod-ом. RabbitMQ хранит имя своего узла по имени хоста, поэтому ему тоже
  нужно постоянное имя.
* **Job** — индексация документации Odoo запускается, работает несколько минут и завершается.
  Deployment перезапускал бы её бесконечно.

**Альтернативы.** PostgreSQL как Deployment с PVC — работает, но при обновлении Deployment
может на время запустить вторую копию на том же томе (две копии PostgreSQL на одних файлах
портят данные). Внешний PostgreSQL (вне кластера) — честнее для production, но для Minikube
система должна подниматься целиком.

**Проверка.** `kubectl delete pod postgres-0` → StatefulSet создал новый Pod с тем же томом,
через несколько секунд запросы к заказам снова отвечали 200, e2e-тест 5/5: администратор и
заказы, созданные до удаления, на месте.

**Почему выбрано.** Каждый тип объекта используется по назначению; данные переживают
перезапуск.

## 3. ConfigMap: настройки вне образа

**Что сделано.** `configmaps/pad-config.yaml` — уровень логов, адреса сервисов
(`http://order-service:8000`), адрес базы (`DATABASE_HOST=postgres`) и брокера, таймауты,
лимит запросов gateway. `rag/rag-config.yaml` — адрес Ollama, модель LLM.
`configmaps/postgres-init.yaml` — скрипт создания баз. В Deployment ConfigMap подключён
целиком (`envFrom`).

**Почему.** Один и тот же образ работает в docker compose и в Kubernetes, отличаются только
переменные окружения. Сервисы лабы 2 уже читают все настройки из окружения (pydantic-settings),
поэтому код менять не пришлось.

**Альтернативы.** Отдельный ConfigMap на каждый сервис — точнее (сервис видит только своё), но
8 почти одинаковых файлов. Лишние ключи сервисы игнорируют (`extra="ignore"`), секретов в
ConfigMap нет, поэтому общий ConfigMap безопасен.

**Ограничение.** Переменные окружения читаются при старте. После `kubectl edit configmap`
нужен `kubectl rollout restart deployment -n pad`.

## 4. Secret: пароли не в Git и не в образе

**Что сделано.** Secret `pad-secrets` создаётся kustomize из файла
`lab3/k8s/secrets/secrets.env`, которого нет в Git (`.gitignore`). Файл делает
`lab3/scripts/make_secrets.py` из `lab2/.env` (те же пароли, что в docker compose). В Git лежат
только шаблоны: `secrets.env.example` и `secret.example.yaml` (как выглядит объект).
Каждый Deployment берёт из Secret **только свои** ключи (`secretKeyRef`): catalog-service
получает пароль только своей базы. Строка подключения собирается в манифесте:
`postgresql+psycopg://orders:$(DB_PASSWORD)@$(DATABASE_HOST):$(DATABASE_PORT)/orders_db`
(пароль из Secret, адрес из ConfigMap).

**Почему.** Требование: паролей в открытом виде в Git быть не должно. Secret в Kubernetes
хранится в base64 — это кодирование, а не шифрование (раскодируется одной командой). Защита в
том, что Secret не лежит в Git, не вшит в образ и выдаётся Pod-у только по явной ссылке.

**Ключ JWT в Kubernetes обязателен.** В лабе 2 при пустом `JWT_PRIVATE_KEY` auth-service
генерировал временный ключ. В Kubernetes это ломается: при двух копиях auth-service у каждой
был бы свой ключ, и токен одной копии не проходил бы проверку ключом другой. Поэтому
`make_secrets.py` отказывается создавать Secret без ключа.

**Альтернативы.**
* `secret.yaml` с паролями в Git — нарушает требование.
* `kubectl create secret generic --from-env-file=...` вручную — работает, но это отдельный шаг,
  который легко забыть; kustomize делает то же самое в общей команде.
* Sealed Secrets / внешнее хранилище (Vault) — шифрованные секреты можно хранить в Git, но нужен
  дополнительный компонент в кластере. Для Minikube избыточно.

**Проверка.** `kubectl describe secret pad-secrets -n pad` — 11 ключей, значения скрыты;
`git status` не показывает `secrets.env`.

## 5. Service: обращение по имени, не по localhost

**Что сделано.** У каждого сервиса Service того же имени (`order-service`), порт 8000.
Внутренние сервисы — тип ClusterIP (адрес только внутри кластера). gateway — тип NodePort
(порт 30080 на узле Minikube), плюс Ingress (раздел 9).

**Почему.** IP Pod-а меняется при каждом пересоздании. Service даёт постоянное имя; встроенный
DNS кластера (служба имён, превращает имя в IP) отвечает на `order-service` адресом Service, а
Service делит запросы между готовыми копиями. Имена совпадают с docker compose, поэтому адреса
`http://inventory-service:8000` в ConfigMap те же, что в лабе 2.

**Проверка.** После `kubectl scale deployment order-service --replicas=3`:
`kubectl get endpoints order-service` → три IP. e2e-тест 5/5 проходит через gateway, который
обращается к сервисам только по именам Service.

## 6. Пробы: startup, liveness, readiness

**Что сделано.** У каждого сервиса три пробы (HTTP GET на порт 8000):

| Проба | Адрес | Параметры | Что делает Kubernetes при неудаче |
|---|---|---|---|
| startupProbe | `/health` | раз в 2 с, до 30 раз (60 с) | пока не прошла, остальные пробы не выполняются; не прошла за 60 с — перезапуск |
| livenessProbe | `/health` | раз в 10 с, 3 неудачи | перезапускает контейнер |
| readinessProbe | `/ready` | раз в 5 с, 3 неудачи | убирает Pod из Service (запросы идут в другие копии), не перезапускает |

`/health` ничего не проверяет (процесс жив). `/ready` проверяет базу; у gateway — что получен
открытый ключ JWT от auth-service; у rag-assistant — что загружен индекс.

**Почему три, а не две.** Сервис при старте ждёт PostgreSQL и создаёт таблицы; пока это идёт,
`/health` не отвечает. Без startupProbe livenessProbe мог бы убить сервис, который просто
медленно стартует. У rag-assistant startupProbe даёт до 5 минут (загрузка индекса и моделей).

**Почему liveness не проверяет базу.** Если упала база, перезапуск сервиса её не починит, а
одновременный перезапуск всех сервисов только добавит нагрузки. Правильная реакция —
перестать слать запросы (readiness).

**Исправление по итогам проверки: RabbitMQ больше не делает сервис неготовым.**
* *Было в лабе 2:* `/ready` должен был отвечать 503, если нет соединения с RabbitMQ.
* *Эксперимент 1:* остановили RabbitMQ (`kubectl scale statefulset rabbitmq --replicas=0`).
  Через 25 с все сервисы по-прежнему отвечали `/ready` 200 и `"rabbitmq": "connected"`.
  Причина: библиотека aio-pika при обрыве сама переподключается и всё это время считает
  соединение открытым (`is_closed = False`). То есть проверка врала.
* *Вопрос:* если исправить проверку, какое поведение правильное? Если брокер упал и `/ready`
  = 503, Kubernetes уберёт из Service **все** копии order, inventory, fulfillment,
  notification — и система перестанет принимать даже заказы, хотя для приёма заказа брокер не
  нужен: событие пишется в таблицу outbox и уйдёт позже (лаба 2, Transactional Outbox).
* *Решение:* `is_connected()` теперь смотрит, есть ли реальное соединение (`transport`), а
  `/ready` показывает RabbitMQ, но без брокера отвечает 200 со статусом `degraded`. База
  по-прежнему обязательна (503 без неё). Изменение в `lab2/libs/pad_common` (app.py, events.py),
  добавлен unit-тест `test_ready_is_degraded_but_200_without_rabbitmq`.
* *Эксперимент 2 (после исправления):* RabbitMQ остановлен → `/ready` order-service:
  `{"status":"degraded","checks":{"database":{"ok":true},"rabbitmq":{"ok":false,"required":false}}}`,
  все Pod-ы 1/1. Заказ `ORD-20261107-8571E1` создан во время простоя брокера (статус
  confirmed, 20:59:47). RabbitMQ запущен снова → задание на сборку для этого заказа появилось в
  21:00:24, то есть событие дождалось брокера в outbox и дошло.

## 7. Ресурсы: requests и limits

**Что сделано.**

| Что | requests (гарантировано) | limits (потолок) |
|---|---|---|
| 6 бизнес-сервисов и gateway | 50m CPU, 128Mi | 500m CPU, 256Mi |
| PostgreSQL, RabbitMQ | 100m CPU, 256Mi | 1 CPU, 512Mi |
| rag-assistant | 250m CPU, 768Mi | 2 CPU, 2Gi |
| rag-indexer (Job) | 500m CPU, 1Gi | 2 CPU, 3Gi |

`m` — тысячная доля ядра процессора (100m = 0,1 ядра). `Mi` — мебибайт. **requests** —
сколько планировщик Kubernetes резервирует на узле для Pod-а; **limits** — больше нельзя:
CPU выше лимита притормаживается, память выше лимита — контейнер убивается (OOMKilled) и
перезапускается.

**Почему такие числа (замер).** В тестовом кластере в простое (`crictl stats`): gateway 50 МБ,
сервисы 72–85 МБ, PostgreSQL 78 МБ, RabbitMQ 144 МБ. Под нагрузкой 1000 запросов за 3 с память
order-service выросла до 86 МБ. Значит 128Mi покрывает обычную работу с запасом ~50%, а 256Mi —
всплески. CPU в простое 0,2–1% ядра, поэтому 50m достаточно для планирования, а 500m не даёт
одному сервису занять весь процессор Minikube.

**Сколько нужно Minikube.** Сумма requests 13 Pod-ов приложения (по 2 копии gateway, order,
inventory): ≈0,95 CPU и ≈2,5 ГБ памяти; пока работает rag-indexer, ещё 0,5 CPU и 1 ГБ. Системные
Pod-ы Kubernetes (API-сервер, etcd, планировщик, DNS) просят ещё около 0,75 CPU. Поэтому
`minikube start --cpus=4 --memory=6g`: с запасом для всплесков до limits.

**Альтернатива.** Без limits проще, но один «утёкший» сервис может занять всю память узла и
уронить соседей. Требование лабы — задать requests и limits.

## 8. Число копий и масштабирование

**Что сделано.** gateway, order-service, inventory-service — по 2 копии; остальные по 1.
Ручное масштабирование: `kubectl scale deployment order-service --replicas=3`.
Дополнительно `extras/order-service-hpa.yaml` — HPA (HorizontalPodAutoscaler, автоматическое
масштабирование): 2–5 копий order-service по загрузке CPU (нужен
`minikube addons enable metrics-server`). Не включён по умолчанию, потому что мешает ручной
демонстрации: HPA возвращает своё число копий.

**Почему копии безопасны.** Сервисы не хранят состояния в памяти. События из RabbitMQ при двух
копиях не обрабатываются дважды: копии читают одну очередь (брокер отдаёт сообщение одной
копии), а повторную доставку отсеивает таблица `processed_events` (лаба 2). Outbox при двух
копиях order-service может отправить событие дважды — получатели пропускают дубль по `event_id`.

**Почему auth-service 1 копия.** При первом запуске он создаёт администратора. Две копии,
стартующие одновременно, попытались бы создать его дважды (одна упала бы на уникальном имени и
перезапустилась). После первого запуска auth-service можно масштабировать: ключ JWT общий.

**Найденное ограничение: лимит запросов gateway считается в каждой копии отдельно.**
* *Эксперимент:* один пользователь отправляет 1000 запросов `GET /api/orders` за ~3 с
  (лимит `RATE_LIMIT_PER_MINUTE=300`).
* *1 копия gateway:* 314 ответов 200, 686 ответов 429 (Too Many Requests, «слишком много запросов»).
* *2 копии gateway:* 626–629 ответов 200, 371 ответ 429.
* *Вывод:* счётчик хранится в памяти копии, Service делит запросы пополам, и фактический
  лимит = 300 × число копий. Для учебного проекта это записано как известное ограничение.
  Исправление для production — общий счётчик в Redis (сервер быстрого хранения ключ-значение)
  или лимит на уровне Ingress (`nginx.ingress.kubernetes.io/limit-rpm`).

**Проверка масштабирования.** `kubectl scale ... --replicas=3` → `rollout status` успешно,
3 Pod-а Running, 3 адреса в endpoints, e2e 5/5.

## 9. Доступ снаружи: port-forward, NodePort, Ingress

**Что сделано.** Три способа, от самого надёжного к самому «настоящему»:
1. `kubectl -n pad port-forward svc/gateway 8080:8000` — gateway на `http://localhost:8080`,
   как в docker compose. Работает при любом драйвере Minikube.
2. NodePort 30080: `minikube service gateway -n pad --url`.
3. Ingress (`ingress/gateway-ingress.yaml`): входной HTTP-прокси кластера (ingress-nginx)
   отправляет запросы на хост `pad.local` в gateway. Нужен `minikube addons enable ingress`.
   Таймаут прокси увеличен до 180 с: ассистент отвечает до 2 минут.

**Почему все три.** На Windows с драйвером Docker адрес узла Minikube недоступен напрямую, и
NodePort/Ingress требуют туннель (`minikube service`, `minikube tunnel`). port-forward работает
всегда — им пользуемся в демонстрации. Ingress показывает, как вход делается в настоящем
кластере. Ingress в требованиях не обязателен; без включённого addon объект ничему не мешает.

**Проверено в облаке:** NodePort (запросы e2e шли на порт 30080). Ingress в тестовом кластере не
проверялся (там нет ingress-nginx) — проверить на ПК (README, шаг 8).

## 10. RAG из лабы 1 в Kubernetes

**Что сделано.** Том `rag-data` (PVC 3Gi). Job `rag-indexer` строит индекс и в конце пишет
метку `/data/.index-ready`. Deployment `rag-assistant` в initContainer (контейнер, который
выполняется до основного) ждёт эту метку и только потом запускает API. `fsGroup: 10001` даёт
пользователю `app` право писать на том. `READY_REQUIRES_LLM=false`: без Ollama ассистент готов
(поиск работает), `/ask` отвечает 503.

**Почему метка, а не просто порядок запуска.** В docker compose был `depends_on:
service_completed_successfully`. В Kubernetes такого нет: все объекты из `kubectl apply`
стартуют одновременно. Если ассистент запустится раньше индекса, он не загрузит индекс и будет
неготов до перезапуска. initContainer решает это без изменения кода лабы 1.

**Почему Ollama не в кластере.** LLM qwen3.5:9b работает на отдельном компьютере HOME-PC с
видеокартой. В Minikube нет GPU, а 9B-модель на CPU отвечала бы минутами. Адрес задаётся в
ConfigMap `rag-config` (`OLLAMA_URL`), по умолчанию `http://host.minikube.internal:11434` —
так из Pod-а виден компьютер, на котором запущен Minikube (туда приходит SSH-туннель на HOME-PC).

**Альтернативы.** Индекс внутри образа (собирать при `docker build`) — образ на сотни МБ больше,
обновление документации требует пересборки. CronJob вместо Job — переиндексация по расписанию;
документация Odoo меняется редко, поэтому достаточно ручного перезапуска Job.

**Проверка.** Индекс построен той же командой `index.sh` (102 файла .rst → 94 документа →
938 chunks), положен на том; initContainer писал `waiting for rag-indexer` до появления метки,
затем `index ready`; ассистент загрузил индекс за 0,55 с, `/api/status` → `all_ready: true`,
`/api/assistant/search "removal strategy FEFO"` через gateway вернул первым раздел «FEFO removal»,
`/api/assistant/ask` без Ollama → 503 с понятным сообщением. Сам Job внутри кластера в облаке не
запускался (у тестового кластера нет выхода в интернет для скачивания документации) — проверить на ПК.

## 11. Безопасность контейнеров в Kubernetes

**Что сделано.** `runAsNonRoot: true`, `runAsUser: 10001`, `allowPrivilegeEscalation: false`,
`capabilities: drop: [ALL]` (контейнер лишается всех особых прав ядра Linux),
`readOnlyRootFilesystem: true` (файлы образа нельзя изменить; для временных файлов — пустая
папка `/tmp` в памяти Pod-а), `seccompProfile: RuntimeDefault` (запрет опасных системных
вызовов), `automountServiceAccountToken: false` (сервису не выдаётся токен доступа к API
Kubernetes).

**Почему.** Если в сервисе найдут уязвимость, атакующий не получит root, не сможет подменить
код и не сможет управлять кластером. Требование «non-root где возможно» выполнено и в образе, и
в манифестах.

**Исключения.** PostgreSQL и RabbitMQ — официальные образы стартуют от root и сами переключаются
на своего пользователя; их не ограничивали. У RAG не read-only файловая система: библиотеки
лабы 1 пишут кэш моделей в домашнюю папку.

**Проверка.** Все Pod-ы сервисов Running с этими настройками, e2e 5/5.

## 12. Обновление без простоя

**Что сделано.** `strategy: RollingUpdate, maxSurge: 1, maxUnavailable: 0`: при обновлении
сначала поднимается новая копия, и только когда она прошла readinessProbe, гасится старая.
У rag-assistant `Recreate` (две копии с индексом в памяти не нужны).
Образы с тегом версии `1.0.0`, а не `latest`, и `imagePullPolicy: IfNotPresent`: Kubernetes не
пытается скачать локальный образ из Docker Hub.

**Пауза перед остановкой (preStop).** Когда Kubernetes останавливает старую копию, он
одновременно посылает ей сигнал остановки и убирает её из Service. Второе доходит до всех
узлов с небольшой задержкой, и в этот момент запросы ещё могут прийти в уже
останавливающуюся копию. Поэтому у каждого сервиса `lifecycle.preStop: sleep 5`: копия ещё 5 с
принимает запросы, пока её убирают из Service, и только потом останавливается.

**Эксперимент.** Во время `kubectl rollout restart deployment gateway order-service` каждые
0,25 с отправлялся запрос `GET /api/orders` через gateway (идёт в order-service).
* без preStop: 158 из 160 ответов 200, один 503 и один обрыв по таймауту;
* с preStop 5 с: 200 из 200 ответов 200.

**Почему выбрано.** Обновление действительно без потерь запросов; цена — остановка Pod-а на 5 с
дольше.

**Как выпускать новую версию.** Собрать с новым тегом (`build-images.ps1 -Tag 1.0.1`),
поменять тег в манифесте → `kubectl apply -k lab3/k8s`. Откат: `kubectl rollout undo
deployment/order-service -n pad` (хранится 3 прошлые версии, `revisionHistoryLimit: 3`).
